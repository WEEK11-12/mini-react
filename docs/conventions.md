# 코드·문서 작성 규칙

상태: 프로젝트 작성 규칙 초안

이 문서는 Mini-React의 이름, 코드 형식, 문서 구성 기준을 정한다. 언어 자체의 필수 문법과 구별되는 프로젝트 관례이며, 기존 요구사항의 기능 범위나 임시 설계 결정을 변경하지 않는다.

## 1. 이름과 파일

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 디렉터리·파일 | 소문자 kebab-case | `dom-reader.ts`, `temporary-decisions.md` |
| 클래스 | PascalCase | `FunctionComponent`, `HistoryStore` |
| 타입·인터페이스 | PascalCase | `VNode`, `PatchPlan`, `Props` |
| 일반 함수·메서드·변수 | camelCase | `readDOM`, `applyPlan`, `currentTree` |
| UI 컴포넌트 함수 | PascalCase | `Cart`, `ProductCard` |
| Hook 함수 | `use`로 시작하는 camelCase | `useState`, `useEffect` |
| 고정 설정 상수 | UPPER_SNAKE_CASE | `MAX_UPDATE_COUNT` |
| 불리언 값·조회 함수 | 의미에 맞는 is/has/can 접두어 | `isMounted`, `hasChanges`, `canBack` |

- `const`로 선언한 모든 변수를 대문자로 쓰지는 않는다. 지역 값과 객체는 `currentTree`, `historyStore`처럼 작성한다.
- DOM·VDOM·HTML 같은 약어는 기존 API 표기를 유지한다. 예: `readDOM`, `VNode`.
- `README.md` 등 도구·플랫폼에서 관례적으로 사용하는 파일명은 예외다.
- 현재 설계 경로인 `docs/design`은 유지한다. 경로를 바꿀 때는 관련 링크·설명·작업 지침도 함께 수정한다.
- 이름만으로 자료형이나 책임이 드러나도록 작성한다. `data`, `temp`, `manager` 같은 포괄적인 이름은 더 구체적인 이름으로 대체한다.

## 2. 모듈과 클래스

파일은 관련 함수·타입·클래스를 묶는 모듈이다. 모든 모듈을 클래스로 만들 필요는 없다.

| 모듈 | 주요 구성 | 책임 |
| --- | --- | --- |
| `diff.ts` | `diff()` 함수 | 이전·다음 VDOM의 차이 계산 |
| `component.ts` | `FunctionComponent` 클래스 | 컴포넌트 실행과 Hook 기록 관리 |
| `history.ts` | `HistoryStore` 클래스 | 이력 저장과 현재 위치 관리 |

- 입력을 받아 결과를 계산하는 작업은 함수로 표현한다.
- 지속되는 상태와 생명주기를 함께 관리할 때 클래스를 고려한다. 상태가 있다는 이유만으로 클래스를 강제하지 않는다.
- 모듈 외부에서 사용하는 API만 export하고, 내부 보조 함수는 공개하지 않는다.
- 기본적으로 named export를 사용한다. 도구가 요구하는 설정 파일 등은 예외다.
- 라이브러리 로직과 웹페이지의 편집·오류 표시 로직을 분리한다.

## 3. 코드 형식과 타입

현재 설계의 TypeScript 선택을 기준으로 한다. JavaScript 파일을 함께 사용하는 경우에도 동일한 명명·형식 규칙을 적용한다.

- 들여쓰기는 공백 2칸, 문자열은 기본적으로 작은따옴표, 문장 끝에는 세미콜론을 사용한다.
- 줄바꿈은 LF, 파일 끝에는 개행을 둔다. 불필요한 줄 끝 공백은 제거한다.
- 재할당하지 않으면 `const`, 재할당하면 `let`을 사용한다. `var`는 사용하지 않는다.
- 외부에 공개하는 함수의 입력·반환 타입과 모듈 사이의 데이터 계약을 명시한다. 지역 변수는 타입 추론을 우선한다.
- 알 수 없는 외부 입력은 `unknown`으로 받고 검사한다. `any`나 타입 단언으로 검증을 대신하지 않는다.
- 변경하지 않을 배열·객체 계약에는 `readonly`를 사용한다. 단, `readonly`는 런타임 불변성이나 깊은 불변성을 보장하지 않는다.
- 오류를 빈 `catch`로 무시하지 않는다. 호출자에게 전달하거나 해당 계층의 오류 정책에 따라 처리한다.

```ts
export function diff(previous: VRoot, next: VRoot): PatchPlan {
  return buildPatchPlan(previous, next);
}
```

위 코드는 형식 예시이며 구현 완료를 뜻하지 않는다. Formatter·Linter를 도입하면 이 기준을 설정 파일에 반영하고, 실제 설정과 문서가 달라지지 않도록 함께 관리한다.

## 4. 주석과 테스트

- 주석은 코드만으로 알기 어려운 이유, 제약, 경계 조건을 설명한다. 코드의 동작을 그대로 반복하지 않는다.
- 함수 계약을 설명할 필요가 있으면 JSDoc으로 입력 조건, 반환값, 오류를 기록한다.
- 남은 작업에는 이유와 관련 요구사항 ID 또는 이슈를 함께 남긴다.
- 단위 테스트 파일은 `*.test.ts`, 브라우저 테스트 파일은 `*.spec.ts`로 구분한다.
- 테스트 이름은 조건과 기대 동작을 드러낸다. 예: `첫 이력에서 뒤로 이동하면 현재 상태를 유지한다`.
- 요구사항 검증 테스트에는 관련 ID를 표시한다. 내부 설계만 검증하는 테스트에 요구사항 ID를 억지로 부여하지 않는다.
- 테스트 결과에는 실행 명령·환경·결과를 기록한다. 미실행 상태를 통과로 표시하지 않는다.

## 6. Markdown 형식

- 파일 첫 줄에 `# 문서 제목`을 하나 둔다. 이후 `##`, `###` 순서로 제목 단계를 사용한다.
- 제목·문단·목록·표·코드 블록 사이에 빈 줄을 한 줄 둔다.
- 설명은 간결한 서술형으로 작성한다. `~한다`, `~이다`를 사용하고 `~해보자` 같은 권유형은 사용하지 않는다.
- 한 문단에서는 하나의 주제를 설명한다. 절차는 번호 목록, 병렬 항목은 불릿, 비교와 대응 관계는 표로 작성한다.
- 줄바꿈을 위해 공백을 반복하거나 빈 줄을 여러 개 넣지 않는다. 표 셀에서 꼭 필요한 줄바꿈은 `<br>`를 사용한다.
- 코드 블록에는 `ts`, `js`, `html`, `mermaid` 등 언어를 표시한다.
- 코드의 이름은 백틱으로 감싼다. 굵은 글씨는 핵심 정의나 상태를 강조할 때만 사용한다.
- 문서 링크는 저장소 내 상대 경로를 사용한다. GitHub Wiki 전용 `[[페이지]]` 문법은 저장소 문서에 사용하지 않는다.

## 7. 요구사항 ID와 연결

- 기존 접두어와 번호를 유지한다. 문서 순서를 바꾸어도 이미 부여한 ID를 재번호화하거나 다른 요구사항에 재사용하지 않는다.
- 요구사항마다 정의·인수 조건·우선순위를 기록하고, 출처·미결정 정책·보충 자료가 있으면 연결한다.
- 관련 ID를 언급할 때는 해당 앵커로 연결한다. 예: [HIST-01](requirements.md#hist-01).
- 명시적 앵커는 기존 문서와 같이 소문자 ID를 사용한다.

```html
<a name="hist-01"></a>
```

```md
[HIST-01](requirements.md#hist-01)
```

## 8. 설계 다이어그램

- 설계 문서의 시각화는 Mermaid로 작성한다. 문자로 그린 박스나 별도 이미지로 중복 관리하지 않는다.
- 각 설계 페이지 앞부분에 전체 구조를 파악할 수 있는 다이어그램을 둔다.
- 데이터와 구성 관계는 클래스 다이어그램, 처리 순서는 흐름도·시퀀스 다이어그램, 상태 전이는 상태 다이어그램을 사용한다.
- 타입·함수 모듈을 클래스 다이어그램으로 표현할 경우 실제 클래스와 구분한다. 유니언 타입의 구성원을 상속 관계로 오해하지 않도록 설명한다.
- 그림에는 핵심 관계를 넣고 세부 계약은 본문에 둔다. 본문과 다이어그램의 이름·흐름을 일치시킨다.
- 수정 후 대상 Markdown 뷰어에서 렌더링을 확인한다. 렌더링을 확인하지 못했다면 그 상태를 명시한다.

## 9. 변경 시 확인

- 외부 동작이나 인수 조건이 바뀌면 요구사항·설계·검증 계획의 영향을 함께 확인한다.
- 내부 구현 방식만 바뀌면 관련 설계를 갱신하고, 요구사항 변경이 필요한지 별도로 판단한다.
- 파일·ID·제목을 바꿀 때 관련 링크와 다이어그램을 점검한다.
- 구현·테스트·검토 상태를 구분하고, 아직 하지 않은 작업을 완료로 기록하지 않는다.
