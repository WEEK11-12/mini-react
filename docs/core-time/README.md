# 요구사항 명세서 작성 방법

미니 React의 보고서형 요구사항 명세서에 담을 내용, 항목별 작성 양식, 사용자 흐름과 완료 기준의 표현 방법을 정리합니다. 구성과 예시는 작성 방식의 제안이며, 완성된 프로젝트 명세서나 팀의 확정 결정은 아닙니다.

## 1. 요구사항과 설계의 구분

| 구분 | 중심 질문 | 미니 React 예시 |
| --- | --- | --- |
| 기능 요구사항 | 무엇을 할 수 있어야 하는가? | 이전 이력으로 이동할 수 있다. |
| 제약 | 어떤 조건을 반드시 지켜야 하는가? | State·Hook은 루트에서만 사용한다. |
| 인수 조건 | 어떤 결과면 요구를 충족했다고 판단하는가? | 이력 이동 후 실제·테스트 영역이 모두 선택한 상태를 표시한다. |
| 설계 선택 | 어떤 방법으로 구현하며 왜 선택하는가? | Virtual DOM을 Python dict 또는 클래스로 표현한다. |
| AI 작업 규칙 | AI가 작업할 때 무엇을 따라야 하는가? | 실제 실행한 검증과 미검증 범위를 구분해 보고한다. |

여기서 완료 기준은 기능의 충족 여부를 판단하는 기준입니다. 코드가 생성되었다는 사실만으로 완료라고 판단하지 않습니다.

### 과제에서 방법을 지정한 경우

일반적으로 자료구조·처리 방식은 설계에서 선택할 수 있습니다. 하지만 이번 과제는 Virtual DOM·Diff·Patch와 FunctionComponent 클래스·hooks 배열을 직접 요구합니다. 이 부분은 **과제의 구현 제약**으로 명세해야 합니다.

반면 dict 사용, 자식 대응 알고리즘, Python 실행 위치는 원문이 정해준 답이 아닙니다. 설계 후보를 비교하고 선택 이유를 남겨야 합니다.

## 2. 기준 명세서와 개발 문서의 관계

보고서형 요구사항 명세서를 기준 원본으로 작성하고, 개발 문서는 그 요구를 참조하도록 구성합니다. 다음은 작성 방식의 제안이며 확정된 팀 운영 규칙은 아닙니다.

```text
과제 원문
  ↓ 요구·제약 추출과 미정 사항 확인
보고서형 요구사항 명세서
  ↓ 팀 검토·합의
requirements.md의 구현·검증 기준 정리
  ↓ 요구를 충족하는 대안 비교
design.md의 구조·API·선택 이유 구체화

```

| 문서 | 담당할 내용 | 다른 문서와의 연결 |
| --- | --- | --- |
| 보고서형 요구사항 명세서 | 목적·범위·요구·출처·사용자 흐름·인수 조건 | 합의 후 요구의 기준 원본으로 관리하는 안 |
| requirements.md | AI와 개발자가 바로 참조할 요구·제약·완료 기준 | 기준 명세서의 요구사항 ID와 버전에 연결 |
| design.md | 구조·데이터·인터페이스·실행 흐름·대안과 비용 | 어떤 요구를 해결하는 선택인지 표시 |
| AGENTS.md | 저장소 읽기·변경·검증·보고 규칙 | 요구·설계 내용을 중복 정의하지 않고 참조 |
| Discussion·이슈·PR | 논의·결정 이유·작업·검증 근거 | 관련 요구사항 ID·문서·커밋 연결 |

보고서와 Markdown을 서로 독립적인 정답으로 유지하지 않습니다. 기준 원본·변경 순서를 정하고, 요구가 바뀌면 관련 설계·테스트도 갱신합니다. 실제 보고서의 편집·배포 형식은 별도로 결정합니다.

현재 requirements.md와 design.md는 보고서 작성 전 만든 초안입니다. 기준 명세서가 합의되면 내용을 대조해 정합성을 맞춰야 합니다.

## 3. 요구사항 명세서 구성안

SRS는 Software Requirements Specification, 즉 소프트웨어 요구사항 명세서를 뜻합니다. 이 자료에서는 요구사항을 정리하는 전체 문서의 의미로 사용합니다. 특정 표준 준수를 선언하거나 방대한 양식을 모두 채우자는 제안은 아닙니다.

| 구성 | 작성할 내용 | 이번 프로젝트의 예 |
| --- | --- | --- |
| 표지·문서 정보 | 제목·버전·작성일·작성자·검토 상태 | 미니 React 요구사항 명세서, 검토 전 초안 |
| 1. 프로젝트 개요 | 배경·목적·사용자·포함 및 제외 범위 | UI 갱신과 상태 관리 원리 재구성 |
| 2. 용어 정의 | 팀이 같은 의미로 사용할 말 | 실제 영역·테스트 영역·Patch·History |
| 3. 기능 요구사항 | 독립적으로 확인할 수 있는 동작 | 초기화·편집·적용·저장·이력 이동 |
| 4. 기술·구현 제약 | 원문과 팀이 정한 필수 조건 | 루트 상태 제한, Python·JavaScript 역할 |
| 5. 품질·검증 요구사항 | 정확성·오류·자원 수명·테스트 기준 | 무관한 DOM 유지, 단위·브라우저 검증 |
| 6. 사용자 흐름·인수 시나리오 | 여러 요구가 연결되는 사용과 경계 예시 | Patch·뒤로가기·앞으로가기 |
| 7. 미결정 사항 | 질문·영향·담당·결정 시점 | 과거 이력에서 새 Patch 시 분기 처리 |

처음에는 한 보고서 안에 작성합니다. 유스케이스·표·그림이 독립적으로 관리할 만큼 커졌을 때만 분리합니다.

## 4. 요구사항 한 항목을 작성하는 방법

### 기본 양식

```text
요구사항 ID와 이름:
요구 동작:
출처: 과제 원문 / 팀 결정 / 추가 제안
필수·선택 여부:
인수 조건:
관련 미결정 사항:
```

이 양식은 작성 제안입니다. 현재 저장소의 FR-* ID와 정식 명세서 ID의 대응은 명세서를 작성할 때 정합니다.

### 예시 요구사항 이전 상태로 이동

**요구 동작:** 사용자는 History에 저장된 이전 상태로 이동할 수 있어야 합니다.

**출처:** 과제 원문 Phase 1의 뒤로가기·앞으로가기 및 양쪽 영역 동기화 요구.

**필수·선택 여부:** 필수.

**원문에서 확인할 수 있는 인수 조건:** 이전 상태로 이동하면 실제 영역과 테스트 영역이 모두 해당 상태를 표시합니다.

**팀에서 구체화할 질문:**

- 뒤로가기 한 번에 한 단계씩 이동하는가?
- 첫 상태에서 뒤로가기를 실행하면 상태를 유지하는가?
- 적용하지 않은 테스트 영역 편집이 있을 때 이동하면 어떻게 하는가?

질문에 대해 합의하면 인수 조건에 반영하고 결정 기록을 연결합니다. 일반적으로 자연스러운 동작이라고 곧바로 과제 원문의 필수 조건으로 표시하지 않습니다.

### 작성 원칙

- 한 항목에 독립적으로 확인할 수 있는 동작을 담습니다. 저장·뒤로가기·앞으로가기를 무조건 하나로 묶지 않습니다.
- 과제에서 정한 요구와 팀이 추가한 조건을 구분합니다.
- “빠르게”, “적절히 처리” 대신 관찰·검증할 수 있는 결과를 적습니다.
- 결과뿐 아니라 오류·경계·미지원 입력도 살핍니다.
- 미정 항목을 확정된 조건이나 구현 완료로 표시하지 않습니다.

## 5. 사용자 흐름과 완료 기준을 구체화하는 방법

각 방법은 별도 문서를 반드시 만들라는 뜻이 아닙니다. 요구사항을 더 명확하게 표현하는 수단으로 선택합니다.

| 방법 | 답할 질문 | 사용할 상황 |
| --- | --- | --- |
| 사용자 스토리 | 누가 무엇을 왜 원하는가? | 기능의 목적을 짧게 전달 |
| 유스케이스 | 어떤 순서로 목표를 달성하는가? | 여러 단계·예외가 연결되는 기능 |
| 인수 조건 | 충족 여부를 어떻게 판단하는가? | 기능·제약·품질 요구의 검증 기준 |
| Given When Then | 특정 상황과 행동에서 결과는 무엇인가? | 순서·입력에 따라 결과가 달라지는 예 |
| 상태표·흐름도 | 상태·분기가 어떻게 이어지는가? | 문장만으로 복잡한 규칙 보완 |

### 사용자 스토리 예시

> 테스트 페이지 사용자로서, 변경 전후를 비교하기 위해 이전 상태로 돌아가고 싶다.

스토리는 목적을 설명합니다. 한 문장만으로 상세 요구와 인수 조건이 완성되는 것은 아닙니다.

### 유스케이스 예시 편집한 내용을 적용

**참여자:** 테스트 페이지 사용자.

**시작 조건:** 초기 로드가 완료되어 실제 영역과 테스트 영역이 표시됩니다.

**기본 흐름:**

1. 사용자가 테스트 영역을 수정합니다.
2. 사용자가 Patch 버튼을 누릅니다.
3. 시스템이 현재 테스트 영역을 Virtual DOM으로 변환합니다.
4. 이전 Virtual DOM과 비교해 변경점을 찾습니다.
5. 변경된 부분을 실제 영역에 반영합니다.
6. 새 Virtual DOM을 History에 저장합니다.

**종료 결과:** 실제 영역에 수정 내용이 반영되고 새 상태가 이력에 저장됩니다.

**명세서에서 결정할 예외:** 변경이 없을 때의 저장, 지원하지 않는 입력, 변경 적용 실패. 위 기본 흐름만으로 이 정책들이 결정된 것은 아닙니다.

### 인수 시나리오 예시

```text
Given: History에 A와 B가 저장되어 있고 현재 B를 표시한다.
When: 사용자가 이전 상태로 이동한다.
Then: 실제 영역과 테스트 영역이 모두 A를 표시한다.
```

이 예시는 기대 동작을 표현하며 실행한 테스트 결과가 아닙니다. Given When Then을 사용하기 위해 별도 자동화 도구를 반드시 설치할 필요는 없습니다.

### 경계 상황을 찾기 위한 상태표

| 현재 상황 | 행동 | 검토할 결과와 상태 |
| --- | --- | --- |
| A·B가 있고 현재 B | 이전 상태로 이동 | 두 영역 모두 A 표시. 원문 요구를 구체적인 예로 표현 |
| 첫 상태 | 뒤로가기 | 상태 유지 등을 팀에서 결정할 필요가 있음 |
| 마지막 상태 | 앞으로가기 | 더 이동하지 않는 처리와 버튼 상태를 결정할 필요가 있음 |
| 과거 상태 | 새 변경 Patch | 이후 이력 삭제·유지 여부 미결정 |
| 테스트 영역에 미적용 편집 존재 | 이력 이동 | 편집 폐기·이동 차단 등의 정책 미결정 |

## 6. 미결정 사항과 변경 관리

정답 동작이 아직 정해지지 않았다면 요구사항에 임의로 채우지 않고 별도 항목으로 기록합니다.

```text
미결정 ID:
질문:
연결된 요구사항:
대안과 결과 차이:
결정 담당:
결정이 필요한 시점:
상태: 미결정 / 결정됨
결정 내용·이유·근거 링크:
```

예를 들어 과거 이력에서 새 Patch를 실행했을 때 이후 이력을 삭제할지는 입력·출력과 사용자 흐름을 바꾸는 정책입니다. 이 정책을 결정한 뒤 요구사항과 인수 조건을 갱신하고, 자료구조와 삭제 방법은 설계에 기록합니다.

요구사항 ID는 같은 의미로 유지합니다. 변경 시 버전·변경 내용·이유·관련 결정 기록을 남기고, 개발용 Markdown·설계·테스트의 영향도 함께 확인합니다. 기존 FR-* ID를 새 명세서에서 세분화한다면 대응 관계를 기록합니다.

## 7. 작성한 명세서 점검 기준

- [ ] 목적·사용자·포함 및 제외 범위가 명확하다.
- [ ] 기능·제약·품질과 구현 방법이 구분되어 있다.
- [ ] 독립적으로 검증할 수 있는 동작에 식별자가 있다.
- [ ] 원문 요구·팀 결정·추가 제안의 출처가 구분되어 있다.
- [ ] 필수·선택 여부와 인수 조건이 적혀 있다.
- [ ] 정상 흐름뿐 아니라 오류·경계·미지원 범위도 확인했다.
- [ ] 미정 정책을 확정된 요구로 쓰지 않았다.
- [ ] 유스케이스·시나리오·상태표가 본문의 요구와 모순되지 않는다.
- [ ] 기준 버전과 변경 기록을 찾고 관련 설계·테스트를 연결할 수 있다.

이 점검은 문서 내용의 검토 기준입니다. 체크했다고 제품 구현이나 테스트가 완료되는 것은 아닙니다.
