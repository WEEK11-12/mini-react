# 검증 계획

> **상태:** 구현 전 테스트 설계. 아래는 실행 결과가 아니라 작성·실행할 테스트의 계약이다.
> **기준:** [요구사항](requirements.md) · [전체 설계](design.md)

## 1. 테스트 원칙

테스트는 **입력 → 관찰 결과 → 관련 요구 ID**를 남긴다. 트리 내용만 비교하면 “부분 갱신”을 증명할 수 없으므로, 성공한 Patch에서 변경과 무관한 실제 DOM 노드의 **참조 동일성**도 확인한다. 실패 경로에서는 화면·History·Hook 상태의 복구를 확인한다.

| 단계 | 범위 | 예정 도구 |
| --- | --- | --- |
| 순수 로직 단위 | VNode 비교, 키 대응, History 상태 전이, 의존성 비교 | [Node 내장 `node:test`](https://nodejs.org/api/test.html) |
| DOM 통합·기능 | 원본 HTML 검사, 실제 DOM 읽기, Patch, 버튼·입력·Hooks | [Playwright](https://playwright.dev/docs/intro) Chromium 브라우저 테스트 |
| 수동 확인 | 오류 문구, 미리보기/실제 영역 구분, 키보드 조작 | 실제 브라우저 |

테스트 도구는 **예정**이며 아직 설치·실행하지 않았다. 구현 단계에서 `npm test`와 `npm run test:e2e`를 정의하고, Playwright 실행용 로컬 서버도 함께 설정한다. 브라우저 테스트가 실패하거나 실행되지 않으면 완료로 표시하지 않는다.

## 3. 대표 시나리오

### Phase 1: 변경 없는 노드 확인

1. `<div><h2>장바구니</h2><p>상품 1개</p></div>`를 초기 상태로 둔다.
2. `h2` DOM 참조를 보관하고 코드의 `p`만 `상품 2개`로 고친다.
3. Patch 전 실제 영역은 `상품 1개`, 미리보기는 `상품 2개`여야 한다.
4. Patch 후 실제 영역은 `상품 2개`이고 보관한 `h2` 참조가 그대로여야 한다. (V-02, D-01, D-04)

### Phase 1: 실패와 이력 분기

1. A → B → C를 Patch하고 B로 뒤로 간다.
2. 잘못된 `<script>`를 입력하면 오류가 보이며 B의 실제 영역·이력은 그대로다.
3. 유효한 D를 입력해 Patch하면 앞으로가기는 비활성화되고 C로 돌아갈 수 없다. (V-03, H-02)

### Phase 2: State·Memo·Effect

1. 장바구니의 상품 수량을 입력해 합계를 바꾼다. 다른 컴포넌트의 DOM 참조는 유지한다.
2. 테마만 바꾼다. 합계 계산 횟수는 증가하지 않고 테마 DOM만 달라진다.
3. 상품 개수를 바꾸면 Effect가 이전 정리를 실행한 뒤 문서 제목을 새 값으로 바꾼다. (C-02, C-04, C-05)

## 4. 완료 판정

- FR-01~17 각각에 연결된 테스트가 작성되고, 현재 코드에서 실행해 통과해야 한다.
- 단위·브라우저 테스트의 **실제 명령, 환경, 통과/실패 수, 실행 날짜**를 README 또는 PR에 기록한다.
- 실패·미실행·수동 확인만 한 항목을 “통과”로 적지 않는다. 요구사항이나 설계가 달라지면 이 추적표와 관련 테스트를 함께 갱신한다.
