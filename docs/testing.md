# 검증 계획

> **상태:** 두 Phase의 구현과 실행 결과를 포함한다. 단위 검증·데모 통합·직접 조작의 증거를 구분한다.
> **기준:** [요구사항](requirements.md) · [전체 설계](design.md)

## 1. 테스트 원칙

테스트는 **입력 → 관찰 결과 → 관련 요구 ID**를 남긴다. 트리 내용만 비교하면 “부분 갱신”을 증명할 수 없으므로, 성공한 Patch에서 변경과 무관한 실제 DOM 노드의 **참조 동일성**도 확인한다. 실패 경로에서는 오류가 난 단계에 따라 커밋 상태의 유지, 화면 내용 복구 또는 후속 작업 중단을 구분해 확인한다.

| 단계 | 범위 | 실행 도구 |
| --- | --- | --- |
| 순수 로직 단위 | VNode, Diff 계획, 키 대응, History 상태 전이, HTML 입력 | [Node 내장 `node:test`](https://nodejs.org/api/test.html) |
| 브라우저 모듈 단위 | 작은 독립 DOM fixture에서 DOM 변환·렌더링·Patch를 직접 호출 | 외부 의존성 없는 `test/browser/index.html` |
| 브라우저 기능 | 격리한 UI fixture에서 편집·버튼·이력을 연결해 검증 | 같은 브라우저 테스트 페이지의 실제 컨트롤러 |
| 수동 확인 | 오류 문구, 미리보기/실제 영역 구분, 키보드 조작 | 실제 브라우저 |

**단위 테스트의 기준은 실행 도구가 아니라 검증 범위**다. DOM API가 필요한 모듈도 작은 fixture에서 해당 모듈을 직접 호출하면 브라우저 단위 테스트로 검증할 수 있다. 전체 데모의 버튼을 눌러 결과를 확인하는 기능 테스트만으로 모듈 단위 검증을 대체하지 않는다.

### Q-01 모듈별 단위 검증 계약

| 모듈 | 분리된 입력·실행 | 직접 관찰할 결과 | 관련 사례 |
| --- | --- | --- | --- |
| DOM → VNode | 실제 영역과 무관한 중첩 DOM fixture를 `readDom`에 전달 | 요소·속성·텍스트·자식 순서, 주석·공백 규칙을 기대 VNode와 비교 | V-01·04 |
| VNode → DOM | 손으로 만든 VNode를 `render`에 전달 | 생성된 DOM의 태그·속성·텍스트·자식 순서를 검사 | V-01 |
| Diff | 이전·다음 VNode만 `diff`에 전달 | 다섯 기본 변경·키 재정렬·동일 트리의 변경 계획을 검사; DOM은 필요하지 않음 | D-01~04 |
| Patch | 독립 DOM 루트와 Diff 계획을 `patch`에 전달 | 목표 내용, 무관한 노드 참조 유지, 적용 실패 시 복구 계약을 검사 | D-01~06 |
| `useState` | 최소 루트 컴포넌트를 mount하고 setter를 직접 호출 | 초기값 보존, 다음 렌더의 새 값, 같은 값 생략·함수형 갱신을 검사 | C-01~03 |
| `useEffect` | 최소 루트 컴포넌트에서 실행·정리 횟수를 기록 | 최초 실행, 의존성별 재실행, 정리 순서, 오류 시 커밋 상태를 검사 | C-04·06 |
| `useMemo` | 계산 횟수를 기록하는 함수를 최소 루트에서 호출 | 동일 의존성에서 결과 재사용, 변경 시 재계산, 계산 예외 처리를 검사 | C-04·06 |

원본 HTML 검사기와 History 전이도 각각 작은 입력으로 별도 단위 검증한다(V-03~05, H-01~03). 위 표의 관련 사례는 검증할 동작의 ID이며, 구현 시 **모듈 단위 테스트와 화면 기능 테스트의 실행 결과를 별도로 기록**한다.

### 실행 방법과 현재 결과

1. Node.js 24 이상에서 `npm test`로 순수 로직을 실행한다. 파일별 프로세스 생성이 `spawn EPERM`으로 차단되는 환경은 `npm run test:in-process`로 실행한다. 격리 없는 실행은 모듈 캐시를 공유하므로 일반 실행과 구분한다.
2. `npm start`로 서버를 실행한다. `http://localhost:5173/test/browser/index.html`을 열면 실제 DOM과 UI fixture를 사용하는 테스트가 자동 실행된다. 결과 목록과 최종 실패 수를 확인한다.
3. `http://localhost:5173`과 `/phase2.html`에서 실제 페이지를 조작한다. 브라우저 fixture 통과와 실제 페이지 직접 조작은 별개의 증거다.

사용자 선택에 따라 외부 패키지·테스트 브라우저를 추가 설치하지 않았다. Playwright 및 `test:browser`·`test:e2e` CLI 명령은 정의하지 않았다. 브라우저 결과는 현재 설치된 브라우저에서 위 페이지를 열어 재현한다.

Phase 2 TDD 기록: 초기 런타임 미구현에서 36개 실패를 확인하고 구현했다. 이후 실제 브라우저에서 지원 범위 검증 실패가 이전 노드를 교체하는 문제, updater 안의 setter 재진입, 복구 실패 후 남은 DOM 정리 문제를 각각 실패 테스트로 재현한 뒤 수정했다. 해당 구현 시점에는 83개 모두 통과했고 이후 호환·시각화 회귀를 추가했다.

TDD 기록: 기존 Diff·History 90개가 미구현 오류로 실패하는 것을 확인한 뒤 구현했다. 브라우저 22개도 DOM·컨트롤러 자리표시자에서 실패한 뒤 통과했다. 이후 NBSP·인접 텍스트를 가진 초기 DOM의 직렬화 실패 두 건을 실제 브라우저에서 재현하고 수정했다. 과거 가짜 구현 검사에서는 항상 빈 계획을 내는 Diff와 무조건 추가하는 History가 테스트에 걸렸다. 이 기록은 모든 가능한 잘못된 구현을 배제한다는 뜻은 아니다.

### 사용 관점별 경계 검토

| 관점 | 재현할 입력·행동 | 기대 결과 · 예정 테스트 |
| --- | --- | --- |
| HTML 편집 초보자 | 루트 앞뒤 공백·완결된 주석, 루트 밖 글자, 주석만 있는 입력, `<p>사과<!-- 메모 -->배</p>` | 하나의 루트만 인정하고 글자·빈 루트는 거부. 주석 양옆 텍스트 경계 유지. V-03·04 |
| 오류를 고치는 사용자 | 잘못된 초안 뒤 다시 유효한 코드, 잘못된 초안에서 뒤로가기 | 이전 유효 미리보기·실제 영역 유지 후 회복, 이동 시 대상 스냅샷으로 초안 폐기. V-03, H-04 |
| 목록을 편집하는 사용자 | 키 있는 항목 재정렬, 키 없는 항목 혼합, 빈 키·중복 키, `__proto__` 키 | 키 있는 기존 노드 재사용, 무키는 같은 위치만 대응, 잘못된 키는 거부. V-05, D-03 |
| 외부 DOM 변조 | 목표 변경이 없는 형제를 외부 코드가 수정한 뒤 Patch | 적용 전 이전 VNode와 DOM의 불일치를 검출하고 복구 시도. D-06 |
| 루트 컴포넌트 작성자 | `renderChild` 안의 Hook, 같은 종류 Hook의 조건부 자리 교환 | 전자는 오류. 후자는 런타임 탐지 불가이므로 작성 규칙·리뷰 대상. C-03 |
| 페이지를 종료하는 사용자 | Effect 정리 함수 예외, unmount 직전 예약된 setter | 나머지 정리·이벤트·DOM 해제를 시도하고 예약 갱신을 취소. C-04·06 |

위 관점은 두 Phase의 테스트에 연결되어 있다. 같은 종류·개수 Hook의 자리 교환 탐지는 지원하지 않으며 작성 규칙·리뷰로 다룬다.

## 3. 대표 시나리오

### Phase 1: 변경 없는 노드 확인

1. `<div><h2>장바구니</h2><p>상품 1개</p></div>`를 초기 상태로 둔다.
2. `h2` DOM 참조를 보관하고 코드의 `p`만 `상품 2개`로 고친다.
3. Patch 전 실제 영역은 `상품 1개`, 미리보기는 `상품 2개`여야 한다.
4. Patch 후 실제 영역은 `상품 2개`이고 보관한 `h2` 참조가 그대로여야 한다. (V-02, D-01, D-04)

### Phase 1: 실패와 이력 분기

1. A → B → C를 Patch하고 B로 뒤로 간다.
2. 잘못된 `<script>`를 입력하면 오류가 보이며 B의 실제 영역·이력은 그대로다.
3. 유효한 D를 입력해 Patch하면 앞으로가기는 비활성화되고 C로 돌아갈 수 없다. (V-03, H-02)

### Phase 2: State·Memo·Effect

1. 장바구니의 상품 수량을 입력해 합계를 바꾼다. 다른 컴포넌트의 DOM 참조는 유지한다.
2. 테마만 바꾼다. 합계 계산 횟수는 증가하지 않고 테마 DOM만 달라진다.
3. 상품 개수를 바꾸면 Effect가 이전 정리를 실행한 뒤 문서 제목을 새 값으로 바꾼다. (C-02, C-04, C-05)
