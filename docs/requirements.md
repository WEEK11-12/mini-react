# 요구사항 명세서

**역할:** 무엇을 왜 만들고 어떤 결과면 완료인지 정의합니다. 해결 구조와 API는 [design.md](design.md), AI 작업 규칙은 [AGENTS.md](../AGENTS.md)에서 관리합니다.

**상태:** AI가 먼저 작성한 논의용 초안. 과제 원문의 요구, 사용자가 선택한 언어 방향, AI가 제안한 완료 기준과 품질 항목이 섞여 있습니다. 아래 FR·NFR·인수 시나리오는 아직 사용자·팀이 항목별로 검토해 채택한 계약이 아니며 모두 미구현·미검증입니다.

요구사항은 [README의 작성 순서](../README.md#요구사항과-설계를-정하는-순서)에 따라 과제 원문과 대조하고, 동작·출처·인수 조건을 함께 결정한 뒤 확정합니다. 이 문서의 문장이나 ID를 근거로 미정 정책을 구현하지 않습니다.

## 1. 목적과 해결할 문제

직접 DOM을 조작하면 데이터 변경 시 관련 화면을 각각 갱신해야 합니다. 전체 DOM을 교체하면 기존 요소·입력·이벤트의 수명도 고려해야 합니다. UI를 함수로 표현하면 호출과 별개로 상태를 보존할 방법이 필요합니다.

이 프로젝트는 데이터에서 UI를 표현하고, 이전·다음 UI를 비교하여 필요한 DOM 변경을 적용하는 작은 라이브러리를 구현합니다. 공개된 React 동작에서 필요한 책임을 추론해 재구성하며, 실제 React 내부 구현을 그대로 복제했다고 주장하지 않습니다.

## 2. 사용자와 사용 흐름

| 사용자 | 기대하는 일 |
| --- | --- |
| 앱 작성자 | 함수·props·State로 UI를 표현하고 상태 변경을 화면에 반영 |
| 데모 사용자 | 테스트 영역 편집·Patch·이력 이동으로 변경 결과 확인 |
| 팀·리뷰어 | 설계 이유와 실행 결과를 실제 코드·테스트에 연결해 확인 |

~~~text
앱: 입력·클릭 → 상태 변경 → 다음 UI 계산 → 변경된 DOM 반영
편집 데모: 실제 DOM 읽기 → 테스트 영역 생성 → 편집 → Patch → 이력 이동
~~~

## 3. 범위와 제약

### 포함

- Phase 1: DOM 읽기·Virtual DOM·Diff·Patch, 실제/테스트 영역, Patch·뒤로가기·앞으로가기.
- Phase 2: FunctionComponent 클래스와 hooks 배열, mount·update, useState·useEffect·useMemo.
- Phase 2의 갱신은 Phase 1의 Diff·Patch를 재사용.
- 단위 테스트·실제 브라우저 기능 검증과 실행 안내.

### 외부 조건과 팀 방향

- 핵심 언어는 Python, JavaScript는 DOM·이벤트 연결에 제한적으로 사용합니다.
- 원본 과제는 Vanilla JavaScript/TypeScript를 명시합니다. Python 예외 허용은 미확인입니다.
- React·Vue 등 외부 UI 프레임워크에 핵심 기능을 위임하지 않습니다.
- State·Hook은 루트에서만 사용하고 자식은 props 기반 순수 함수로 제한합니다.
- 전체 2주에는 Redis·DBMS도 포함됩니다. 미니 React만의 일정·역할은 미정입니다.

### 현재 제외

React 전체 API 호환, JSX, Fiber·동시성·SSR, 자식별 State·Hook, 범용 플러그인 구조는 목표가 아닙니다. Batching·key 기반 재정렬·차별화 기능은 필수 경로 검증 후 검토합니다.

## 6. 인수 시나리오의 시작점

### AC-01. 최초 로드와 Patch — FR-02~05, FR-12

- Given: 실제 영역에 지원하는 샘플 DOM이 있다.
- When: 페이지를 열고 생성된 테스트 영역의 텍스트를 수정한 뒤 Patch한다.
- Then: 실제 영역에 수정이 반영되고 무관한 요소는 같은 DOM 객체로 남는다.

### AC-02. 이력 이동 — FR-13

- Given: 서로 다른 상태를 두 차례 정상 적용했다.
- When: 뒤로가기 후 앞으로가기를 누른다.
- Then: 각 이력에 맞게 실제·테스트 영역이 함께 바뀐다.

### AC-03. 상태 갱신 — FR-06~08

- Given: 루트 State의 숫자가 0이고 자식이 props로 이를 표시한다.
- When: 증가 동작을 한 번 수행한다.
- Then: 루트·자식의 표시가 1로 바뀌고 다른 State는 유지된다.

이 시나리오는 검증할 기대 동작이며 실행 결과가 아닙니다. Effect·Memo·실패·경계 시나리오는 해당 계약을 선택하며 추가합니다.

## 8. 완료와 변경 기준

관련 기능·경계 테스트, DOM 의존 기능의 실제 브라우저 검증, 실행 안내와 제한 기록이 있어야 검증됨으로 표시합니다. 구현됨과 검증됨은 구분합니다.

요구가 바뀌면 같은 변경에서 설계·테스트 기준도 수정합니다. 진행 상황·실행 결과·기여는 요구사항 ID와 커밋을 연결해 이슈·PR·Discussion에 기록합니다. 기존 세부 문서의 ID·미채택 제안은 이번 초안의 확정 계약이 아닙니다.
