# 미니 React 요구사항 명세서

> **상태:** PR 검토용 초안. 과제에서 지정한 기능과 이 문서의 제안을 구분해 기록한다. 구현·테스트 완료를 뜻하지 않는다.
> **기준 자료:** [팀 저장소의 과제 원문](https://github.com/WEEK11-12/mini-react/blob/main/docs/assignment.md)
> **관련 문서:** [설계](design.md) · [검증 계획](testing.md) · [작성 가이드](guides/requirements-specification.md) · [AI 작업 규칙](../AGENTS.md)

## 1. 개요와 목적

이 프로젝트는 Virtual DOM, Diff, Patch와 함수형 컴포넌트·State·Hooks를 직접 구현하고, 사용자의 입력·클릭에 따라 화면의 필요한 부분이 바뀌는 웹 페이지로 검증한다. 데이터가 바뀔 때 여러 DOM 요소를 직접 갱신하는 부담과, 컴포넌트 함수가 다시 실행되어도 State를 유지해야 하는 문제를 다룬다.

이 문서는 **무엇이 동작해야 하고 어떤 결과면 충족되는지**를 정한다. 자료구조·알고리즘·모듈 경계 등 해결 방법은 [설계 문서](design.md)에 기록한다. 구현자·리뷰어·AI는 동일한 ID로 요구, 설계, 테스트 결과를 연결한다.

## 2. 범위

| 구분 | 내용 |
| --- | --- |
| 필수 · Phase 1 | 실제 DOM 읽기, Virtual DOM 변환·렌더링, Diff·Patch, 편집 가능한 테스트 영역, Patch와 State History 탐색 |
| 필수 · Phase 2 | 함수형 컴포넌트, 루트 State, useState·useEffect·useMemo, Phase 1 갱신 경로 재사용 |
| 필수 · 검증 | 핵심 모듈의 단위 테스트와 브라우저 기능 테스트 |
| 선택·확장 후보 | Batching과 추후 팀이 결정할 차별화 기능 |

실제 React의 전체 API·내부 구현과의 호환성은 요구하지 않는다. 선택·확장 후보는 필수 기능의 완료 기준에 포함하지 않는다.

### Phase 1 테스트 HTML의 지원 범위

코드 입력창에는 HTML을 입력하되, 미리보기와 Patch가 지원하는 범위는 다음으로 제한한다. 이 범위는 장바구니 예시의 텍스트·속성 변경, 자식 추가·삭제, 요소 교체를 모두 확인하기 위한 프로젝트 결정이다. Phase 2 데모의 버튼·입력창에는 이 목록을 적용하지 않는다.

| 구분 | 지원 대상 |
| --- | --- |
| 요소 | `div`, `h2`, `p`, `strong`, `ul`, `li`, `span` |
| 속성 | `class`, `title`, `data-*` (`data-` 뒤에 이름이 있어야 함) |
| 내용 | 지원 요소 안의 텍스트와 자식 요소의 순서 |
| 최상위 구조 | 지원 요소 하나로 시작한다. 빈 입력이나 최상위 요소 둘 이상은 오류다. |
| 작성 문법 | 모든 요소의 닫는 태그를 명시하고 올바르게 중첩한다. 속성값은 작은따옴표 또는 큰따옴표로 감싼다. |
| 주석·공백 | 주석과 들여쓰기용 공백은 Virtual DOM에 담지 않는다. 화면에서 단어를 띄우는 공백은 보존한다. |

지원하지 않는 요소·속성이나 프로젝트의 입력 규칙을 벗어난 코드는 오류를 표시하고 미리보기는 마지막으로 유효했던 상태를 유지한다. 오류가 해소될 때까지 Patch를 실행하지 않는다. [HTML 표준](https://html.spec.whatwg.org/multipage/grouping-content.html#the-p-element)이 일부 닫는 태그의 생략을 허용하더라도 이 프로젝트에서는 허용하지 않는다. 문자 참조·중복 속성·공백 판별의 구체적 규칙은 [입력 설계](design/html-input.md)에 **팀 검토용 제안**으로 기록했다.

## 3. 기능 요구사항

각 기능을 **ID · 요구 동작 · 출처 · 우선순위 · 인수 조건** 한 행으로 기록한다. 표는 기능 묶음별로 나눠 비교하기 쉽게 한다. 인수 조건은 테스트할 상황과 관찰 결과를 제시하며, 추가 정책의 결정 상태는 6장에 둔다.

**ID 표기 규칙:** 아래 접두어는 이 프로젝트에서 문서를 연결하려고 정한 약속이며, 특정 표준이 강제한 약어가 아니다.

| 접두어 | 뜻 | 이 문서에서 가리키는 것 |
| --- | --- | --- |
| `FR` | Functional Requirement | 시스템이 제공해야 할 기능·동작 |
| `CON` | Constraint | 구현에 적용되는 기술·컴포넌트 제약 |
| `Q` | Quality | 품질·검증 기준 |
| `OPEN` | Open question | 원래 미정이었던 항목의 결정 추적 번호. 현재 확정·제안 상태는 6장 참조 |
| `D` | Design decision | [설계 문서](design.md)의 선택과 이유 |

`FR-01`의 `01`은 **FR 안에서 부여한 고유 참조 번호**다. Phase, 중요도, 구현 순서를 나타내지 않는다. 다른 문서·테스트에서 같은 ID를 참조하므로, 문서 순서가 바뀌어도 기존 번호를 재사용하거나 다시 매기지 않는다. 새 항목에는 해당 접두어의 다음 번호를 붙인다.

### 3.1 Virtual DOM 변환·렌더링

| ID | 요구 동작 | 출처 | 우선순위 | 인수 조건 |
| --- | --- | --- | --- | --- |
| FR-01 | 페이지가 로드되면 실제 영역의 샘플 HTML을 읽어 Virtual DOM 트리로 변환한다. | 과제 Phase 1 | 필수 | 2장의 지원 범위에 포함된 요소·속성, 텍스트와 자식 순서가 변환 결과에 표현된다. |
| FR-02 | FR-01에서 만든 트리로 테스트 영역의 미리보기를 렌더링한다. | 과제 Phase 1; 미리보기 구성은 프로젝트 결정 | 필수 | 최초 로드 후 미리보기는 실제 영역의 샘플과 같은 지원 대상 내용을 표시한다. |

### 3.2 Diff·Patch

| ID | 요구 동작 | 출처 | 우선순위 | 인수 조건 |
| --- | --- | --- | --- | --- |
| FR-03 | 두 Virtual DOM을 비교해 바뀐 위치와 내용을 찾는다. | 과제 Phase 1; 기본 사례는 사용자 선택 | 필수 | 동일한 두 트리에는 변경이 없고, 아래 다섯 사례에서는 해당 변화가 구분된다. |
| FR-04 | Diff 결과를 실제 영역에 적용해 변경된 부분을 갱신한다. | 과제 Phase 1 | 필수 | 적용 후 실제 영역에 목표 내용이 표시되고, 변경과 무관한 DOM 요소는 교체되지 않는다. |
| FR-05 | Patch를 누르면 테스트 영역의 현재 미리보기 DOM을 다시 Virtual DOM으로 만들고, 이전 트리와 비교한 뒤 FR-04를 실행한다. | 과제 Phase 1; HTML 코드 편집 방식은 프로젝트 결정 | 필수 | HTML 코드를 수정해 미리보기에서 확인한 뒤 Patch를 누르면 그 변경이 실제 영역에 반영된다. |

**FR-03의 기본 검증 사례**

| 기본 사례 | 장바구니 예시 | 기대 결과 |
| --- | --- | --- |
| 텍스트 변경 | `상품 1개` → `상품 2개` | 기존 텍스트의 변경 식별 |
| 속성 변경 | `class="empty"` → `class="filled"` | 속성 변경 식별 |
| 자식 추가 | 목록에 사과 추가 | 삽입 위치와 새 자식 식별 |
| 자식 삭제 | 목록에서 사과 삭제 | 제거할 자식 식별 |
| 요소 교체 | `<p>합계</p>` → `<strong>합계</strong>` | 종류가 달라진 요소 식별 |

자식 목록의 식별은 **`data-key` 우선, 키가 없으면 위치 기준**으로 한다. 키는 형제 사이에서만 유일해야 한다는 조건과 중복 키의 오류 처리는 설계 초안의 제안이다. 순서만 바뀐 키 있는 요소는 동일 DOM 요소로 이동할 수 있어야 한다. (FR-03~04)

### 3.3 편집 화면·History

| ID | 요구 동작 | 출처 | 우선순위 | 인수 조건 |
| --- | --- | --- | --- | --- |
| FR-06 | 실제·테스트 영역, Patch·뒤로·앞으로 버튼과 테스트 영역의 HTML 코드 입력창·미리보기를 제공한다. | 과제 Phase 1; 코드 편집·오류 정책은 프로젝트 결정 | 필수 | 유효한 편집은 미리보기만 바꾸고, 잘못된 편집은 아래 경계 표대로 처리한다. |
| FR-07 | 성공적으로 변경된 Virtual DOM을 State History에 저장한다. | 과제 Phase 1 | 필수 | 서로 다른 상태를 순서대로 적용하면 각 상태를 History 탐색으로 다시 표시할 수 있다. |
| FR-08 | 뒤로가기를 누르면 History의 이전 Virtual DOM으로 이동한다. | 과제 Phase 1 | 필수 | 이전 상태가 있을 때 실제 영역과 테스트 영역이 함께 그 상태를 표시한다. |
| FR-09 | 앞으로가기를 누르면 History의 다음 Virtual DOM으로 이동한다. | 과제 Phase 1 | 필수 | 뒤로 이동한 뒤 다음 상태가 있을 때 실제 영역과 테스트 영역이 함께 그 상태를 표시한다. |

**FR-06의 입력 경계**

| 입력 상태 | 관찰 결과 |
| --- | --- |
| 유효한 코드로 편집 | 미리보기만 갱신. Patch 전 실제 영역·History 유지. |
| 미지원 요소·속성, 닫는 태그 누락·중첩 오류, 빈 입력·복수 루트, 따옴표 없는 속성값 | 오류 표시. 마지막 유효 미리보기·실제 영역·History 유지. Patch 차단. |
| 오류를 고쳐 다시 유효해짐 | 오류 해제, 새 미리보기 표시, Patch 재활성화. |

**History 경계:** 뒤로 간 뒤 다른 상태로 Patch하면 기존 앞으로가기 이력을 삭제한다(사용자 결정). 처음에서 뒤로, 끝에서 앞으로는 상태를 바꾸지 않는다. 같은 트리의 Patch는 이력 항목을 늘리지 않는다. 미적용 편집 초안에서 이동하면 대상 상태의 코드·미리보기·실제 영역을 함께 복원한다. 마지막 두 규칙은 팀 검토용 제안이다. (FR-07~09)

### 3.4 컴포넌트·State

| ID | 요구 동작 | 출처 | 우선순위 | 인수 조건 |
| --- | --- | --- | --- | --- |
| FR-10 | UI를 함수형 컴포넌트로 표현하고, 이를 감싸는 `FunctionComponent` 클래스에 `hooks` 배열·`mount()`·`update()`를 제공한다. | 과제 Phase 2 | 필수 | 최초 표시에는 `mount()`, 상태 변경 후 갱신에는 `update()`가 사용되며 컴포넌트 함수의 반환 결과가 UI에 반영된다. |
| FR-11 | 루트 컴포넌트의 State는 컴포넌트 함수가 다시 실행되어도 보존된다. | 과제 Phase 2 | 필수 | 한 상태를 바꾼 뒤 다시 렌더링해도 그 값과 변경하지 않은 다른 상태의 값이 유지된다. |
| FR-12 | 자식 컴포넌트는 부모가 전달한 props로 UI를 표현한다. | 과제 Phase 2 | 필수 | 루트가 전달하는 props가 바뀌면 자식의 표시가 그 값에 맞게 바뀐다. 자식은 자체 State·Hook을 사용하지 않는다. |

### 3.5 Hooks

| ID | 요구 동작 | 출처 | 우선순위 | 인수 조건 |
| --- | --- | --- | --- | --- |
| FR-13 | `useState`는 루트 컴포넌트의 값을 렌더링 사이에 보존하고, 갱신 요청 시 다시 렌더링한다. | 과제 Phase 2 | 필수 | 클릭으로 값을 바꾸면 다음 렌더링에서 새 값이 읽히고 화면 표시가 갱신된다. |
| FR-14 | `useEffect`는 루트 컴포넌트에서 렌더링 결과와 연결된 외부 작업을 실행할 수 있게 한다. | 과제 Phase 2 | 필수 | 최초 표시와 관련 값 변경 시 Effect의 실행 여부를 확인할 수 있다. 의존성·정리 함수의 세부 계약은 [Hook 설계](design/component-hooks.md)의 팀 검토용 제안을 따른다. |
| FR-15 | `useMemo`는 루트 컴포넌트에서 계산 결과를 재사용할 수 있게 한다. | 과제 Phase 2 | 필수 | 관련 입력이 같으면 이전 계산 결과를 재사용하고, 달라지면 다시 계산한다. 비교 규칙은 [Hook 설계](design/component-hooks.md)의 팀 검토용 제안을 따른다. |

### 3.6 Phase 2 화면 갱신·데모

| ID | 요구 동작 | 출처 | 우선순위 | 인수 조건 |
| --- | --- | --- | --- | --- |
| FR-16 | State 변경 후 컴포넌트가 새 Virtual DOM을 만들고, 이전 트리와의 Diff·Patch로 실제 DOM을 갱신한다. | 과제 Phase 1·2 연계 | 필수 | 상태 변경에 필요한 부분만 DOM에 반영되고, 변경되지 않은 요소는 유지된다. |
| FR-17 | 사용자의 입력 또는 클릭에 따라 화면이 바뀌는 브라우저 데모를 제공한다. | 과제 테스트 페이지 개발 | 필수 | 실제 브라우저에서 사용자 동작 → State 변경 → 화면 갱신을 재현할 수 있다. |

## 4. 기술·컴포넌트 제약

| ID | 제약 | 출처 |
| --- | --- | --- |
| CON-01 | HTML·CSS·Vanilla JavaScript를 사용한다. React·Vue 등 외부 UI 프레임워크를 사용하지 않는다. | 과제 원문 기술 스택; JavaScript 중심 팀 선택 |
| CON-02 | State와 Hook은 최상위 루트 컴포넌트에서만 관리한다. | 과제 원문 Phase 2 |
| CON-03 | 자식 컴포넌트는 자체 State 없이 props만 받아 사용하는 순수 함수로 만든다. | 과제 원문 Phase 2 |

## 5. 품질·검증 기준

| ID | 기준 | 확인 방법 |
| --- | --- | --- |
| Q-01 | Virtual DOM 변환, Diff, Patch와 세 Hook을 모듈 단위로 검증한다. | 각 모듈의 단위 테스트 결과 |
| Q-02 | Phase 1의 편집·Patch·이력 이동과 Phase 2의 입력·클릭 갱신을 브라우저에서 검증한다. | 재현 가능한 기능 테스트 |
| Q-03 | 다양한 태그·요소와 경계 사례를 검토한다. | 지원 범위·기대 결과·테스트 기록 |
| Q-04 | 핵심 동작과 실제 React와의 차이를 설명할 수 있게 기록한다. | 설계 이유·구현 한계·검증 근거 |

테스트를 작성했다는 사실과 통과했다는 사실을 구분한다. 실제 실행 전에는 완료로 표시하지 않는다.

## 6. 결정 상태와 검토 항목

테스트 영역의 코드 입력·미리보기 방식, 지원 요소·속성, 단일 루트·명시적 닫기·따옴표, 오류 보존, 주석 무시·의미 있는 공백 보존 원칙은 사용자와 정했다. 폼의 현재 값과 이벤트 처리는 Phase 1 비교 범위에서 제외한다. 아래 `OPEN` ID는 **추적용**이며, “제안”을 팀 합의로 읽지 않는다.

| ID | 현재 상태와 담당 문서 | 영향 |
| --- | --- | --- |
| OPEN-01 | **제안:** 문자 참조 범위·중복 속성 오류를 [HTML 입력 설계](design/html-input.md)에 정의. | FR-01~02, FR-05~06 |
| OPEN-02 | **제안:** 줄바꿈 포함 공백 노드를 들여쓰기로 제외하는 기준을 [HTML 입력 설계](design/html-input.md)에 정의. | FR-01~05 |
| OPEN-03 | **확정:** 뒤로 간 뒤 새 Patch는 미래 삭제. **제안:** 같은 트리 Patch·경계 버튼·소스 복원은 [History](design/history.md)에 정의. | FR-07~09 |
| OPEN-04 | **제안:** Hook 슬롯·의존성·Effect 정리와 실패 동작을 [컴포넌트·Hooks](design/component-hooks.md)에 정의. | FR-10~16 |
| OPEN-05 | **제안:** Phase 2 장바구니 데모. 차별화 기능은 필수 기능 1차 완료 후 논의. | FR-17 |
| OPEN-06 | **제안:** Node 내장 단위 테스트와 Playwright Chromium 기능 테스트. 실행 명령·결과는 구현 후 검증. [검증 계획](testing.md) 참조. | Q-01~03 |

요구사항을 바꾸면 같은 변경에서 관련 설계와 테스트 기대 결과를 함께 갱신한다. 아직 채택하지 않은 제안도 구현 전에 팀이 검토할 수 있도록 구체적 계약으로 적었다.
