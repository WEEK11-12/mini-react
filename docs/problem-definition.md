# 문제 정의 — 왜 UI 라이브러리를 만드는가?

상태: 설계 초안. 공식 사실의 출처는 [참고 자료](references.md)에 연결합니다.

## 1. 화면은 프로그램의 데이터와 맞아야 한다

HTML은 문서 구조를 표현하는 텍스트이고, DOM은 브라우저가 문서를 노드·객체로 다루도록 제공하는 인터페이스입니다. 프로그램은 DOM을 통해 문구·구조·속성을 바꿀 수 있습니다. DOM은 JavaScript 언어 자체와 같은 개념이 아닙니다. [S-01: MDN DOM](references.md)

~~~text
데이터: count = 2
화면: "횟수 2", "짝수", "두 배 4"
~~~

클릭으로 count가 3이 되면 세 표현 모두 갱신되어야 합니다. 일부 문구만 바꾸면 데이터와 화면이 어긋납니다.

## 2. 해결할 문제

### P-01. 같은 데이터가 여러 화면에 나타난다

변경 위치를 각자 찾아 갱신하면 화면이 늘어날수록 누락 지점도 늘어납니다. 원하는 결과를 선언하고 변경 계산을 공통 경로에 맡길 수 있어야 합니다.

### P-02. 전체 교체는 기존 요소의 정체성을 잃게 할 수 있다

HTML 문자열로 자식들을 통째로 교체하면 기존 input·버튼과 새 요소는 다른 DOM 객체입니다. 포커스·선택·외부 참조·이벤트도 고려해야 합니다. innerHTML 대입은 자손을 교체하며, 신뢰하지 않는 입력을 그대로 넣으면 주입 문제가 생길 수 있습니다. [S-08: MDN innerHTML](references.md)

부분 갱신은 이 문제를 줄이는 수단입니다. 모든 상황에서 최적 성능이라는 뜻은 아닙니다.

### P-03. 함수의 재실행과 상태의 수명이 다르다

함수로 UI를 표현하면 재사용하기 쉽지만 호출 때 만들어진 지역 변수만으로 다음 호출의 상태를 보존할 수 없습니다. 컴포넌트 수명에 속하는 저장 공간이 필요합니다.

### P-04. 화면 계산과 외부 작업이 섞이면 실행 시점을 추적하기 어렵다

컴포넌트 실행 중 매번 타이머·이벤트·구독을 생성하면 중복과 누수가 발생할 수 있습니다. 의존하는 값과 이전 작업의 정리 시점을 표현해야 합니다.

### P-05. 반복 계산과 정확성의 책임을 구분해야 한다

동일 입력의 비싼 파생 계산은 재사용할 수 있습니다. 캐시는 계산 비용을 줄이는 도구여야 하며, 캐시가 없어져도 UI 의미는 같아야 합니다.

## 3. 해결 방향

~~~text
현재 State + props → UI 함수 → 다음 화면 데이터
                                   ↓
이전 화면 데이터 ────────────── 비교 → 변경 적용 → DOM
~~~

개발자는 현재 데이터에서 원하는 화면을 표현합니다. 라이브러리는 상태 수명·변경 계산·DOM 반영을 공통 관리합니다.

React 공식 문서는 render를 컴포넌트 호출을 통한 화면 계산으로, commit을 DOM 변경 반영으로 구분합니다. 매번 모든 DOM을 삭제한다는 의미가 아닙니다. [S-02: React render/commit](references.md)

## 4. 사용자와 성공 기준

| 사용자 | 필요한 일 | 관찰할 결과 |
| --- | --- | --- |
| 앱 작성자 | 상태·props로 UI 표현 | setter 후 관련 문구·자식 출력이 함께 갱신 |
| 편집 데모 사용자 | 수정·비교·이력 탐색 | Patch·이력 이동이 양쪽 영역에 반영 |
| 유지보수자 | 책임과 영향 추적 | 순수 Diff를 DOM 없이 검증하고 오류 경로 추적 |
| 학습자·리뷰어 | 설계와 동작 연결 | 요구사항의 API·ADR·테스트·코드를 찾아 설명 |

## 5. 대안과 비용

| 방법 | 유리한 상황 | 비용·한계 |
| --- | --- | --- |
| 직접 DOM 조작 | 작고 고정된 화면 | 여러 화면과 데이터의 동기화를 직접 관리 |
| 전체 HTML 교체 | 재생성해도 되는 단순 화면 | DOM 정체성·이벤트·폼 상태 유지 문제 |
| Virtual DOM 비교 | UI 표현과 DOM 조작 분리 | 트리 생성·비교·보관 비용 추가 |
| 세밀한 반응성·템플릿 | 변경 추적의 다른 유효한 방식 | 이번 비교·Patch 목표와 다른 설계 경로 |

Virtual DOM은 유일 해법이 아닙니다. 이번에는 UI 표현과 변경 계산의 경계를 관찰하고 외부 조건을 충족하기 위해 선택합니다. 세부 알고리즘은 [ADR-0003](decisions/0003-reconciliation.md)의 제안입니다.

## 6. 목표·비목표

목표는 데이터와 DOM 결과의 일치, 무관한 DOM 정체성 보존, 함수 실행과 상태 수명 분리, 명시적인 Effect·Memo 계약, Python과 브라우저 경계의 검증입니다.

현재 비목표는 다음과 같습니다.

- React 전체 API 호환, JSX, Fiber·동시성·Suspense·SSR 구현.
- 실제 React보다 빠르다는 주장, 전역 최소 편집 거리 보장.
- 자식별 Hook, 여러 루트, 라우터·플러그인 생태계.
- 편집 스냅샷 이력을 브라우저 방문 이력이나 전체 앱 상태 복원으로 취급.

확장이 필요하면 요구사항과 비용을 먼저 변경합니다.

## 7. 역엔지니어링의 증거 수준

공개 동작과 공식 설명에서 필요한 책임을 추론해 재구성합니다. React 내부 소스를 그대로 재현했다는 뜻은 아닙니다.

~~~text
관찰: 숫자를 갱신해도 input DOM 객체가 유지된다.
요구: 관련 없는 DOM을 통째로 교체하지 않는다.
추론: 이전 결과와 다음 결과를 대응시킬 정보가 필요하다.
우리 선택: 위치·종류 기반 비교를 먼저 검토한다.
검증: DOM 객체 정체성과 변경 기록을 검사한다.
~~~

우리 선택을 실제 React 내부 알고리즘의 증거로 사용하지 않습니다. 소스 분석 시에는 저장소·버전·커밋·함수 위치를 별도 기록합니다.
