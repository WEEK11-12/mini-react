# 학습·기여 기록

제품 계약은 [API 명세](api-contracts.md), 설계 이유는 [ADR](decisions/README.md), 실행 근거는 [테스트 전략](testing.md)에 연결합니다. 이 문서는 개인의 이해와 기여를 기록하며 제품의 동작 기준을 별도로 만들지 않습니다.

## 1. 기록 목적

대화 전체를 옮기기보다, 질문·판단·실험을 통해 이해가 바뀐 지점을 남깁니다. 포트폴리오 문장은 이 기록의 코드·테스트 근거를 확인한 뒤 작성합니다.

- 개인 판단, 팀 결정, AI 설명·작성, 실제 실행 결과를 구분합니다.
- 설명을 읽었다는 사실과 직접 설명·검증할 수 있다는 사실을 구분합니다.
- 검증 전에는 가설 또는 현재 이해로 기록합니다.
- 관련 개념이 나오면 필요한 만큼 학습하고 구현·실험으로 연결합니다.

## 2. 시작점 — 2026-11-06 문서 작성 기준

- 사용자는 DOM에 익숙하지 않고 React 사용 경험도 기억나지 않는다고 설명했습니다.
- AI가 실제 코드를 주로 작성하되, 사용자는 문제·필요성·설계 이유·핵심 실행 흐름을 이해하고 설명하는 방식을 원합니다.
- 팀은 공통 언어 C·Python 중 Python을 선택했습니다. 과제 허용 여부·실행 구조는 미확정입니다.
- 현재 이 저장소에서 구현 및 테스트를 실행한 근거는 없습니다.

## 3. 첫 질문: React는 DOM을 매번 전부 지우는가?

- 관련 요구사항: P1-04, P2-06, Q-04.
- 사용자 질문: DOM이 문서 객체 구조라면 React가 매번 이를 지우고 새로 만드는 방식인지 궁금했습니다.
- AI가 설명한 내용: 다음 UI를 계산하는 작업과 실제 DOM을 변경하는 작업은 다릅니다. 결과에 차이가 있을 때 필요한 변경을 적용하며, 구조 변화에 따라 일부 노드는 교체될 수 있습니다.
- 참고: [React 공식 Render and Commit](https://react.dev/learn/render-and-commit).
- 아직 확인하지 않은 것: 사용자의 재설명, 이 프로젝트에서 실제 DOM 객체가 유지되는 동작.
- 다음 실험 제안: 텍스트만 바꾸고 무관한 input의 변경 전후 DOM 객체가 동일한지 확인합니다.
- 상태: 개념 설명 제공. 구현·실험 미실행.

```text

질문 또는 관찰한 문제:
처음 생각한 동작과 이유:
설명·공식 자료·관련 코드:
실험 방법과 예상 결과:
실제 결과와 근거:
달라진 이해:
내 말로 설명한 핵심 흐름:
남은 질문·다음 행동:
```

## 6. 기여 기록 양식

```text
작업 / 관련 커밋·PR:
관련 요구사항 ID:
개인: 직접 판단·설계·검토·검증한 내용
팀: 공동 결정 및 다른 팀원의 담당 내용
AI: 설명·제안·작성·수정한 내용
검증 담당자와 실제 결과:
내가 설명할 수 있는 범위:
아직 이해하거나 검증하지 못한 범위:
```

AI가 만든 코드를 팀원이 이해·검증했다고 해서 직접 전부 작성한 것으로 기록하지 않습니다. 반대로 AI가 작성했다는 이유로 사람이 수행한 설계 판단·검토·검증을 누락하지 않습니다.
