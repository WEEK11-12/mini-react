## 후속 제한 재검토 — 정책 채택과 화면 확인

2026-11-11 운영 에이전트의 정책 동기화를 실제 diff와 요구사항 본문으로 재검토했다. **맞음 — 기존 선택의 채택과 인수 조건 반영은 앞선 설계 경계에 부합한다.** 이번 변경에서 필수 제약 약화나 새로운 설계 blocker는 발견하지 않았다. 아래 원래 결론·잔여 표는 최초 검토 시점의 이력으로 유지하며, 후속 해결 상태는 이 절을 따른다.

- **정책 채택 기록 해결:** requirements의 기능 인수 조건·3.4·5.2·6절, AGENTS와 설계 현재 상태에 채택이 반영되었다. PATCH-03은 VDOM과 실제 폼 값이 모두 같은 경우의 무쓰기와 네이티브 값 보정을 구별한다. EFF-04는 권장이라는 출처를 유지하면서 이번 완료 범위에 포함했다. Effect 오류의 성공 커밋 유지·계속 처리와 updater/렌더/검증·한도 실패의 대기열 폐기를 구별한다. OPEN-10은 실제 최종 검증한 Playwright Chromium 및 기록된 버전으로 제한하며 다른 엔진·실기기 지원을 주장하지 않는다.
- **과거 기록 보존 확인:** stage-01~09의 변경은 당시 기록이라는 상단 주석 추가이며, 기존 실패 수치·제한 승인·미실행 내용을 통과로 고치지 않았다. 제품 소스·앱 진입 HTML·앱 package 설정에는 기준 HEAD 대비 diff가 없었다. 병행 수정 중인 테스트의 동작 적합성은 이번 제한 검토 대상이 아니다.
- **실제 화면 확인 증거 추가:** 운영 담당의 `tests/reports/final-ui/report.md`와 이미지 산출물 존재를 확인했다. 보고 환경은 HeadlessChrome 145.0.0.0, 1440×1100 및 390×844 viewport다. 설계 검증 담당은 `desktop-phase-one.png`, `narrow-metrics-help.png`, `narrow-invalid-input.png`를 직접 판독해 영역·첫 행동 안내, 계측의 누적/실패/해제 한계 설명, 오류 상태의 유효 미리보기 표시를 대조했다. 기존의 ‘화면 확인 미실시’는 보고된 관찰 범위에서 해소되었다. 조작 전체를 독립 재실행하거나 초회 사용자 이해도·모든 접근성·실기기를 검증한 것은 아니다.
- **증거 해석 주의:** `browser-observations.json`에는 preview가 빈 문자열인 초기 관찰만 남아 있으며, 보고서는 중간 빈 입력을 거친 관찰과 이후 단일 input 재확인을 구분한다. 최종 오류 화면에는 ‘유효 미리보기’가 보이지만 이 이미지만으로 전후 동일성을 증명하지 않는다. 해당 JSON을 최종 보존 재검사의 원본 증거로 인용하지 않고, 기능 보존 판정은 최종 독립 테스트 결과와 함께 연결한다.
- **종결 기록 잔여:** 재검토 시점에 `docs/implementation/stage-10.md`는 아직 생성되지 않아 새 최종 기록 링크는 미해결이었다. 예정된 종결 문서 생성 후 링크 검사와 실제 Chromium 버전·runner 결과 연결이 필요하다. 화면 검토용 browser harness 버전을 Playwright runner의 실행 버전으로 대체하지 않는다. 최종 runner와 전체 키보드 동작 검증은 구현 검증 담당 결과를 기다리며 이번 판정으로 통과 처리하지 않는다.

## 결론

**맞음 — 현재 구현 정책을 변경하지 않고 완료 기준으로 채택하는 방향은 과제의 필수 제약과 양립한다.** 과제는 전체 HTML·모든 브라우저·실제 React의 전체 동작을 요구하지 않는다. 명시적인 지원 범위, 루트 전용 Hook·State, 공통 Diff·Patch, 실패 시 보존·중단 경계를 유지한다면 새 아키텍처 결정은 필요하지 않다.

다만 **설계 검토 완료, 정책 채택, 구현 검증 완료는 서로 다른 상태**다. 이 기록은 OPEN 항목을 단독으로 정식 채택하거나 현재 전체 테스트 통과를 선언하지 않는다. 운영 에이전트가 위임받은 판단으로 아래 기준을 요구사항 본문·결정 기록에 반영하고 구현 검증 결과와 대조해야 전체 완료를 판정할 수 있다. 기존 임시 결정과 단계별 실패 기록은 당시 이력으로 보존한다.

## 완료 기록에 반영할 보완과 경계

1. **문서 상태 보완:** 검증 계획의 ‘아직 작성·실행하지 않았다’는 일괄 표기는 실제 테스트 파일·단계 기록과 맞지 않아 수정했다. 개별 검증 계획을 일괄 통과로 바꾸지는 않았다.
2. **대기열 계약 보완:** 실패·연속 갱신 상한 이후 남은 요청의 처리 의미를 [런타임](component-runtime.md#업데이트-실행-규칙)에 명시했다. `component.ts:66-108,164-167`의 기존 폐기·독립 재시도 동작을 설명한 것이며 정책이나 코드를 변경하지 않았다.
3. **요구사항 동기화:** 정책 채택 시 OPEN 표만 바꾸지 말고 VDOM-02, EDIT-01, EFF-02/04, MEMO-02/03, HIST-01/02/03 및 관련 State·오류·환경 인수 조건에 위 기준을 연결한다. EFF-04의 권장이라는 출처는 남기고 ‘이번 범위에 채택’과 구분한다. AGENTS·설계 목차·결정 기록의 현재 미채택 표기도 함께 갱신해야 한다.
4. **무변경의 경계:** PATCH-03의 ‘변경이 없으면 DOM 수정 없음’은 VDOM뿐 아니라 실제 지원 폼 값도 목표와 같을 때다. 실제 폼 값이 이탈한 경우 HIST-01과 렌더러가 요구하는 보정 쓰기는 허용한다. 이 예외를 요구사항 본문에도 명시하면 두 계약을 서로 모순되게 읽지 않는다.
5. **보수적 복구:** 현행 런타임은 mountTree/applyPlan 내부 오류가 준비 단계인지 구별하지 않고 복구 후 faulted로 종료한다(`component.ts:129-138`). ‘DOM 변경 전 실패’ 보존 검증은 렌더·VDOM 검증과 구분해야 한다. 준비 실패를 판별해 실행을 유지하는 최적화는 현재 인수 조건으로 추가하지 않는다.
6. **호스트 책임:** 이벤트 오류 UI·faulted 컨테이너의 inert·포커스 이동은 앱 호스트의 책임이다. 이벤트 바인딩 모듈 자체가 모든 사용자 콜백 예외를 UI로 전달하거나 사용자 함수의 외부 자원 해제를 보장한다고 확대 해석하지 않는다.
